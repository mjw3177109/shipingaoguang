# BasketCut AI V0.2 视觉候选工作流

## 范围与限制

这是真实视觉 GPU 研究链路，不是“自动识别命中/助攻/球员”。COCO 类别的 sports ball 可能漏掉快速或被遮挡的小篮球；篮筐 ROI 必须人工框选，画面固定机位时效果更合适。

目前 V0.2 **已实现**：
- 每场比赛最多两个可视化篮筐 ROI 的交互标定和数据库持久化；
- 受身份权限限制的 `vision-config/` JSON 下载；
- `highlights/vision/` Torchvision 预训练模型逐帧检测 sports ball，支持 CPU/CUDA；
- 仅在指定篮筐邻近区域聚合篮球观测，至少两次观测才生成“可能精彩”候选；
- JSON schema V2：比赛编号、视频时长、分析元数据、是否因最大帧数而截断、候选；
- 受权限限制的 JSON 导回（ID/时长核对、去重、默认待审）；
- CI 里无需 GPU 的 ROI 逻辑/租户安全/导入验收测试。

## 真实操作顺序

1. 运行 V0.1 Django 工作台，打开比赛详情视频。
2. 暂停到篮筐出现画面，点击【开始框选篮筐】，拖出紧贴篮圈的矩形。最多两处；点击【完成框选】后【保存篮筐位置】。
3. 点击【下载 GPU 配置 JSON】，得到 `game-<ID>-hoops.json`。
4. 准备**同一个未经重新剪辑的视频文件**与配置（重新编码造成时长变化超过 3 秒会拒绝）。
5. Kaggle 创建私有 Dataset，上传获得授权的录像和配置。不要公开球员录像。
6. Kaggle 新建 Notebook，选择 GPU，导入仓库下 `notebooks/kaggle_shot_candidates_v02.ipynb`，根据实际路径修改 `VIDEO_PATH` 和 `CONFIG_PATH`。
7. 第一次下载模型权重需要网络，允许 Notebook 使用互联网；检查 GPU 额度及模型权重许可。
8. 运行 Notebook，会生成 `/kaggle/working/candidates.json`。分析元数据里若 `incomplete_scan=true`，只能代表扫描过的视频前段。
9. 回 Django 同一场比赛页面【导入 Kaggle / GPU 篮筐附近候选】。
10. 人工跳转确认每条片段，通过、剔除或调整时间，填入球员编号后批量导出。

## 命令行使用（本地 / 商业云 GPU）

在已安装 PyTorch、Torchvision、OpenCV 的独立推理容器中运行，切勿把这些大型依赖装入基础 Web 镜像：

```bash
pip install -r requirements-vision.txt
python -m highlights.vision.cli --video game.mp4 --config game-1-hoops.json --out candidates.json --device auto --interval 1.5 --max-frames 1800 --threshold 0.35
```

默认每 1.5 秒抽取 1 帧，最多 1800 帧（仅覆盖视频前约 45 分钟）；GPU 显存、处理时长和候选召回率需要用真实视频测量。若视频超过 45 分钟，本默认设置明确标记 `incomplete_scan`；可以调整采样和最大帧数，但会增加运行时间。

输出中 `score` 是篮球检测框的**检测置信度**，不是“进球概率”。框选篮筐过大、镜头来回切换或相机移动会显著降低效果。

## 数据与授权边界

- 不公开上传未获授权的视频，不把原始视频写入公共 GitHub 或 Notebook 日志。
- Django 的基础 Web 进程不运行 Torchvision 推理，不保持常驻昂贵的 GPU。
- COCO 检测预训练模型并不一定适合精确篮球计分。上线商用前必须审查所选模型及权重的授权、拍摄同意、肖像与隐私管理。
- 现阶段扫码领取、按场馆计费、生产级远端任务队列、真实 AI 命中判定都没有实现；后续独立迭代。

## V0.2 验收与下一版门槛

**CI 门槛**：Django migrate 无变更、系统检查、单元测试、短视频 FFmpeg 回归全部通过。

**需现场验证**：至少 10 段已授权的 5V5/3V3 篮球录像，分别记录：
- 每场人工标记的真实投篮尝试总数、候选召回率；
- 每 10 分钟候选误报数、分镜审核用时；
- GPU 帧速率、整个录像耗时和是否截断；
- 每 30/60 分钟原片的总费用。

成功指标可设为“人工确认后覆盖超过 70% 的投篮尝试”，**属于测试目标，不是已实现的效果承诺**。
